# ADR-0030: Hand-written ORM models with DTO value objects as typed jsonb

- **ID:** ADR-0030
- **Timestamp:** 2026-11-20T22:10+01:00
- **Status:** Accepted
- **See:** SPEC §12.2, DOMAIN.md

## Decision

SQLAlchemy models are written by hand in `<module>/models.py`, and migrations are autogenerated from them
(`mise run migration`). Document-shaped fields reuse the DTO types directly: `PydanticJSONB(TypeAdapter(T))` in
`core/models.py` stores a value object (`Condition`, `Routing`, `list[Step]`, `ChannelPreferences`, …) in a `jsonb`
column and validates it on load, so `Mapped[Condition]` is the same type the API exposes. Migrations render these
columns as plain `JSONB` and never import application types. An integration test fails when the models and the
migrations drift apart (`alembic check`).

Considered and rejected:

| Option | Why not |
|---|---|
| Generate models from the DTOs / OpenAPI | No maintained generator. DTOs lack foreign keys, delete rules, indexes and the columns the API never shows (token hashes, `retry_at`, sessions), and their shape differs from the tables (`Owner` union → two columns + check). |
| SQLModel (one class for table and DTO) | Breaks the router → service → models split and the `banned-api` rule; weak with discriminated unions and jsonb. |
| Database first (DDL, then `sqlacodegen`) | Reverses the existing Alembic workflow; loses typed jsonb, `uuid7` defaults and `lazy="raise"`; regenerating overwrites edits. |

## Rationale

- The value objects are defined once, so the database holds exactly what the contract validates.
- Generation still happens where it is reliable: models → migrations.
- Everything stays checked by `ty`; no `Any` columns.
